Скользящее окно решает задачи про **непрерывные** подотрезки: подстроки, подмассивы, серии подряд идущих элементов. Ключевое слово — непрерывные: если элементы можно брать вразнобой, это другая тема.

## Откуда берётся выигрыш

Наивное решение перебирает все подотрезки: O(n²) штук, и на каждый ещё O(n) на пересчёт суммы или состава — итого до O(n³).

Инсайт в том, что **соседние окна почти одинаковы**. Сдвинули окно на единицу — один элемент вошёл справа, один вышел слева. Всё остальное не изменилось. Значит вместо пересчёта с нуля достаточно двух операций.

## Две схемы

**Фиксированный размер.** Окно всегда длины k, оба конца двигаются синхронно. «Максимальная сумма k подряд идущих», «среднее по k последним».

**Переменный размер.** Скелет всегда один и тот же:

```js
let left = 0;
for (let right = 0; right < n; right += 1) {
  // 1. расширяем: включаем nums[right] в состояние окна

  while (/* окно стало недопустимым */) {
    // 2. сжимаем: исключаем nums[left], left += 1
  }

  // 3. окно допустимо — обновляем ответ
}
```

Меняется только «состояние окна» (сумма, счётчики символов, количество нулей) и условие допустимости. Всё остальное — шаблон.

## Как распознать задачу на окно

Формулировки-маркеры: «самый длинный подотрезок, такой что…», «кратчайший подотрезок, такой что…», «не более k чего-то», «ровно k различных».

Если условие звучит как выбор («какие именно нули перевернуть»), **переформулируй его в свойство окна**: «окно, в котором не более k нулей». Выбор исчезает — остаётся шаблон.

<Note title="Почему это O(n), а не O(n²)">
  Внутри внешнего цикла есть `while` — кажется, что вложенность даёт квадрат. Но `left` только
  растёт и никогда не возвращается назад, значит за весь алгоритм он сделает максимум n шагов.
  Суммарно два указателя проходят по массиву по разу каждый: 2n операций, то есть O(n).
</Note>

## Когда окно НЕ работает

Схема требует **монотонности**: расширение окна должно ухудшать условие, сжатие — улучшать.

Для суммы это верно только на неотрицательных числах. На входе `[2, -5, 10]` добавление элемента может уменьшить сумму, и вся логика «расширяем, пока мало» разваливается. Там нужны префиксные суммы с хеш-таблицей — другой приём.

## Ловушки

- **Длина окна — это `right - left + 1`**. Потерянная единица занижает ответ ровно на 1 и проходит половину тестов.
- **`while`, а не `if` при сжатии.** После одного шага сжатия окно может всё ещё быть недопустимым.
- **Счётчики уменьшаются по значению, а не по индексу.** `freq.set(left, …)` вместо `freq.set(s[left], …)` — ошибка, которую видно только на конкретных входах.
- **Удаляй ключ на нуле.** Если оставить запись со значением 0, `map.size` соврёт про количество различных элементов.

## Что в теме

1. **Максимальная сумма окна длины k** — фиксированное окно, самая чистая иллюстрация выигрыша.
2. **Кратчайший подмассив с суммой ≥ target** — переменное окно, сжатие до минимума.
3. **Максимум единиц при k заменах** — переформулировка условия и та самая «+1».
4. **Подстрока с k различными символами** — состояние окна как счётчик частот.
5. **Одинаковые буквы при k заменах** — самое хитрое условие допустимости в теме.
