## Задача

`retry(fn, { attempts, delay })` повторяет вызов при ошибке. `attempts` — максимальное число **попыток** (не повторов), `delay(n)` возвращает паузу перед n-й повторной попыткой. Все попытки провалились — пробрасываем последнюю ошибку.

## Главная ловушка: `return` без `await`

```js
// ❌ ошибка пролетит МИМО catch
try {
  return fn();
} catch (error) {
  // сюда не попадём: fn() вернула промис, а не бросила синхронно
}
```

`fn()` возвращает промис. Синхронный `try/catch` ловит только синхронные исключения — отклонённый промис через него проходит насквозь, и `retry` не повторит ничего.

```js
// ✅ await превращает отклонение в исключение внутри try
try {
  return await fn();
} catch (error) { ... }
```

Это тот случай, когда `return await` **не** избыточен, вопреки распространённому совету. Внутри `try` он обязателен.

## Пауза только между попытками

```js
if (attempt < attempts) await sleep(delay(attempt));
```

После последней провалившейся попытки ждать нечего — мы всё равно бросаем ошибку. Лишняя пауза добавляет задержку на ровном месте, и на цепочке ретраев это накапливается.

## Backoff

`delay(n)` — функция от номера попытки, а не константа. Это позволяет реализовать стратегии:

```js
delay: (n) => 100                    // фиксированная
delay: (n) => 100 * n                // линейная
delay: (n) => 100 * 2 ** n           // экспоненциальная
delay: (n) => 100 * 2 ** n + Math.random() * 50   // + jitter
```

**Jitter** (случайная добавка) важен в проде: без него все клиенты, упавшие одновременно, повторят запрос тоже одновременно и добьют сервис. Классическая проблема «громового стада».

## Что стоит добавить в реальном коде

- **Не повторять то, что не поможет.** 4xx-ошибки повторять бессмысленно — предикат `shouldRetry(error)`.
- **Общий дедлайн.** Пять попыток по 10 секунд — это 50 секунд ожидания. Обычно нужен лимит на всю операцию.
- **`AbortSignal`.** Чтобы отменить цепочку извне.

## Сложность

Время — сумма времён попыток плюс пауз. Память — O(1).
