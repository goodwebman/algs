## Задача

Дан массив, **отсортированный по возрастанию**, и число `target`. Нужно найти два разных элемента, дающих в сумме `target`, и вернуть их индексы.

Задача выглядит учебной, но встречается в проде постоянно: «найти два платежа, которые в сумме дают спорную сумму», «подобрать пару тарифов под бюджет», «свести две отсортированные выгрузки».

## Наивное решение и почему оно плохо

Первое, что приходит в голову — перебрать все пары:

```js
for (let i = 0; i < nums.length; i += 1) {
  for (let j = i + 1; j < nums.length; j += 1) {
    if (nums[i] + nums[j] === target) return [i, j];
  }
}
```

Это работает и даёт O(n²). На массиве из 30 000 элементов — примерно 450 миллионов сравнений. И самое обидное: этот код **не использует то, что массив отсортирован**. Он вёл бы себя точно так же на перемешанном входе.

Когда решение не использует данное в условии свойство — почти всегда есть решение лучше.

## Инсайт: инвариант отрезка

Поставим два указателя на края: `left = 0`, `right = n - 1`. Посмотрим на сумму `nums[left] + nums[right]`.

**Инвариант:** если ответ существует, он целиком лежит внутри отрезка `[left, right]`.

Пусть сумма оказалась *меньше* target. Что мы знаем про `nums[left]`? Он в паре с самым большим доступным элементом дал слишком мало. Значит с любым другим элементом отрезка (а все они ≤ `nums[right]`) он даст ещё меньше. Вывод: **`nums[left]` не входит в ответ ни в какой паре** — его можно выбросить, сдвинув `left` вправо. Инвариант при этом сохраняется.

Симметрично: если сумма больше target, выбрасывается `nums[right]`.

Это не эвристика и не «попробуем подвигать указатели». Это доказательство: каждый шаг гарантированно отбрасывает элемент, который в ответе быть не может. Отрезок сужается на единицу за шаг, значит шагов не больше n.

<Note title="Почему это работает только на отсортированном массиве">
  Весь аргумент держится на фразе «все остальные элементы отрезка не больше `nums[right]`». На
  неотсортированном входе она ложна, и выбросить элемент нельзя — там нужен другой приём, через
  хеш-таблицу.
</Note>

## Сложность

**Время — O(n).** Каждый шаг цикла двигает ровно один указатель навстречу другому. Суммарное расстояние между ними — n, значит шагов не больше n. Внутри шага — константная работа.

**Память — O(1).** Две переменные-индекса, ничего не аллоцируется. Это главное преимущество перед решением через `Map`, которое даёт то же O(n) по времени, но тратит O(n) памяти.

## Ловушки

- **`left <= right` вместо `left < right`.** При `left === right` мы складываем элемент сам с собой и можем вернуть неверный ответ на входе вроде `[4], 8`. Условие обязано быть строгим.
- **Пустой массив.** `right = -1`, цикл не выполняется ни разу, возвращается `null` — корректно. Но если писать `do…while`, всё сломается.
- **Массив не отсортирован.** Алгоритм молча вернёт неверный ответ. Если сортировка входит в решение, помни: она стоит O(n log n) и уничтожает исходные индексы.
- **Переполнение.** В JS чисел с фиксированной разрядностью нет, но при суммах больше `Number.MAX_SAFE_INTEGER` точность теряется — тут нужен `BigInt`.

## JS-специфика

`nums[left]` на плотном массиве чисел — это прямая адресация в памяти, действительно O(1). Но если массив «дырявый» (`const a = []; a[1000] = 5;`), V8 переводит его в hash-режим, и доступ по индексу перестаёт быть константным. Такой массив создаётся случайно — например, через `delete a[i]` или присваиванием по индексу за пределами длины.

Проверить форму можно в Node: `node --allow-natives-syntax` и `%DebugPrint(arr)` — в выводе будет `PACKED_SMI_ELEMENTS` (хорошо) или `HOLEY_ELEMENTS` / `DICTIONARY_ELEMENTS` (плохо).
