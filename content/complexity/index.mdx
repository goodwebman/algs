Big-O отвечает на один вопрос: **как растёт время работы, когда растёт вход**. Не «сколько миллисекунд» — это зависит от машины, движка и погоды. А именно форма роста: в два раза больше данных — во сколько раз дольше?

## Читаем код и считаем

Правило одно: считай, сколько раз выполнится самая внутренняя операция, и оставь только самое быстрорастущее слагаемое.

```js
for (let i = 0; i < n; i += 1) {        // n раз
  for (let j = 0; j < n; j += 1) {      // × n раз
    doSomething();                       // = n² операций
  }
}
```

Константы и младшие слагаемые отбрасываются: `3n² + 100n + 5000` — это O(n²). Не потому что константы не важны, а потому что при достаточно большом n они перестают влиять на **форму** кривой.

## Шесть классов, которые встречаются в жизни

| Класс | Типичный источник | n = 1000 |
|---|---|---|
| O(1) | доступ по индексу, `Map.get` | 1 операция |
| O(log n) | бинарный поиск, высота сбалансированного дерева | ~10 |
| O(n) | один проход по массиву | 1 000 |
| O(n log n) | сортировка сравнением | ~10 000 |
| O(n²) | вложенный цикл, перебор пар | 1 000 000 |
| O(2ⁿ) | перебор всех подмножеств, наивная рекурсия | больше атомов во вселенной |

Практическое правило: **на входе до 10⁶ ищи O(n) или O(n log n)**. Если получается O(n²) — вход до 10⁴. Если O(2ⁿ) — до 20–25 элементов, и то с мемоизацией.

## Худший, средний, лучший

Big-O описывает **верхнюю границу**, обычно для худшего случая. Но иногда важны все три:

- **Быстрая сортировка:** средний O(n log n), худший O(n²) — если каждый раз выбирать неудачный опорный элемент.
- **Хеш-таблица:** средний O(1), худший O(n) — если все ключи попадают в одну корзину.
- **Поиск в отсортированном массиве:** лучший O(1) — если искомое оказалось ровно посередине.

Когда говорят «алгоритм за O(1)», почти всегда имеют в виду средний или амортизированный случай.

## Амортизация — не то же самое, что средний случай

`array.push()` обычно O(1). Но когда внутренний буфер заканчивается, движок выделяет новый (обычно вдвое больше) и **копирует всё** — это O(n).

Значит push — это O(n)? Нет. Ключ в том, что дорогая операция случается тем реже, чем она дороже: копирование n элементов происходит после n дешёвых вставок. Раскидав стоимость по всем операциям, получаем **амортизированно O(1)**.

Разница со «средним случаем» принципиальна: средний случай — про вероятность (может повезти, может нет), амортизация — про гарантию на серию операций. Последовательность из n `push` **всегда** займёт O(n) суммарно, без всякого «в среднем».

<Note title="Где амортизация ломается">
  Если после каждого `push` делать `pop` ровно на границе перевыделения, можно заставить движок
  перевыделять буфер на каждой операции. На практике V8 от этого защищается, не сжимая массив
  сразу, но сам приём — стандартный способ построить худший случай для амортизированных структур.
</Note>

## Память считается так же

O(1) по памяти — значит используется фиксированное число переменных, независимо от размера входа. Два указателя — O(1). Копия массива — O(n). Матрица n×n — O(n²).

**Рекурсия тратит память на стек вызовов.** Рекурсивный обход дерева глубины h — это O(h) памяти, даже если ничего не аллоцируется явно. Для вырожденного дерева h = n, и на 100 000 узлов будет `RangeError: Maximum call stack size exceeded`.

## Чего Big-O не говорит

- **Про константы.** O(n) с тяжёлой константой может проигрывать O(n log n) с лёгкой на реальных размерах. Именно поэтому в сортировках маленькие подмассивы досортировывают вставками, а не рекурсией.
- **Про кэш процессора.** Проход по массиву подряд в разы быстрее, чем по связному списку той же длины, хотя оба O(n): массив лежит в памяти непрерывно и попадает в кэш.
- **Про то, какие n бывают на самом деле.** Если n всегда меньше 10, лучший алгоритм — самый простой.

## Проверь руками

Теория теорией, а замер честнее. В любой задаче учебника есть кнопка «Замерить рост»: решение прогоняется на входах разного размера, и результат ложится поверх теоретических кривых. Напиши намеренно квадратичное решение и посмотри, как замер уйдёт вверх по параболе.
