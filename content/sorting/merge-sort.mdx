## Задача

Отсортировать массив. Ради учебы — написать merge sort, а не вызвать `sort`.

## Инсайт: разделяй и властвуй

Рекурсивно режем массив пополам, пока не останутся одиночные элементы. Один элемент отсортирован по определению. Дальше сливаем пары отсортированных кусков обратно — и на каждом уровне слияния получается вдвое более длинный отсортированный отрезок.

**Слияние двух отсортированных массивов — линейная операция.** Смотришь на головы обоих, забираешь меньшую, повторяешь. Никаких вложенных циклов, никаких сравнений «каждый с каждым».

Глубина рекурсии — log n уровней. На каждом уровне суммарно сливается n элементов (по кускам). Итого n × log n.

## Почему `<=`, а не `<`

```js
const takeLeft = right >= to || (left < mid && nums[left] <= nums[right]);
```

Строгое `<=` при равенстве: берём элемент из **левой** половины. Ровно это сохраняет исходный порядок равных элементов — делает сортировку **стабильной**. Поменяешь на `<` — стабильность теряется, и на объектах с равными ключами порядок поедет.

## Сложность

**Время — O(n log n) на любом входе.** В отличие от быстрой сортировки, merge sort не деградирует: уже отсортированный массив и перемешанный стоят одинаково.

**Память — O(n)** на буфер слияния. Это главный минус: merge sort не сортирует на месте. Отсюда его редко берут как «основную» сортировку в стандартных библиотеках.

**Стабильность — да.** Благодаря `<=` при равенстве.

## Ловушки

- **Буфер вне рекурсии.** Выделять буфер на каждом слиянии — это O(n log n) памяти и лишний allocation pressure. Буфер заводится один раз на весь массив и переиспользуется.
- **Полуинтервалы, а не `[from, to]`.** `[from, to)` — стандарт для индексов в таких алгоритмах: `to` не включается, `mid = (from + to) / 2`, слияние идёт `[from, mid)` и `[mid, to)`. С включённым `to` постоянно путаешься в ±1.
- **Рекурсия на отрезке длины 1.** Базовый случай — `to - from <= 1`, выходим без работы. Без него бесконечная рекурсия.
