Бинарный поиск — это не «поиск в отсортированном массиве». Это **поиск границы в монотонном пространстве ответов**, и вторая формулировка в разы полезнее первой.

## Классическая форма

Отрезок `[left, right]` содержит ответ. Смотрим на середину, сравниваем с целью, выбрасываем половину, где ответа быть не может. Отрезок сокращается вдвое за шаг → O(log n).

Для миллиона элементов это 20 шагов. Для миллиарда — 30. Логарифм растёт настолько медленно, что практически ведёт себя как константа.

## Форма поважнее: поиск границы

Представь массив булевых значений, полученных из монотонного условия:

```
F F F F T T T T
        ^ первая T — это ответ
```

Условие обязано быть **монотонным**: став истинным, оно не может снова стать ложным. Тогда бинарный поиск найдёт границу.

Эта форма отвечает на кучу вопросов, где никакого «искомого элемента» вообще нет:

- первое вхождение значения в массиве с дубликатами (`nums[i] >= target`);
- позиция вставки, чтобы не сломать порядок;
- минимальная скорость поедания бананов, при которой успеваешь за h часов;
- минимальная вместимость корабля, при которой груз увозится за d дней;
- квадратный корень целочисленно (`i * i <= n`).

Последние три — это **бинарный поиск по ответу**: перебирается не индекс массива, а само значение ответа. Массива может не быть вовсе.

<Note title="Как понять, что задача решается бинпоиском">
  Спроси: «если ответ X подходит, подойдёт ли X+1 автоматически?» Если да — пространство ответов
  монотонно, и можно искать границу. Формулировки-маркеры: «минимальное значение, при котором…»,
  «максимальное значение, такое что…».
</Note>

## Два шаблона, и лучше знать оба

**Поиск точного значения:**

```js
let left = 0, right = n - 1;      // right — ИНДЕКС
while (left <= right) {           // нестрогое: отрезок из одного элемента валиден
  const mid = left + ((right - left) >> 1);
  if (a[mid] === target) return mid;
  if (a[mid] < target) left = mid + 1;
  else right = mid - 1;           // mid проверен и выброшен
}
return -1;
```

**Поиск границы:**

```js
let left = 0, right = n;          // right — ГРАНИЦА, на единицу за массивом
while (left < right) {            // строгое: сходимся в точку
  const mid = left + ((right - left) >> 1);
  if (predicate(mid)) right = mid;  // mid может быть ответом — не выбрасываем
  else left = mid + 1;
}
return left;                      // == n, если условие не выполнилось нигде
```

Разница в трёх местах: начальный `right`, строгость сравнения в `while` и что делаем с `mid`. Перепутать их — самый надёжный способ получить бесконечный цикл.

## Почему бесконечный цикл

Если в ветке не двигать границу «сквозь» mid, отрезок перестанет сокращаться. Классика:

```js
// ❌ зависнет на отрезке из двух элементов
if (a[mid] < target) left = mid;   // должно быть mid + 1
```

При `left = 0, right = 1` середина равна 0, `left` остаётся 0, и так навсегда.

**Правило:** хотя бы в одной ветке mid обязан выбрасываться (`mid + 1` или `mid - 1`), и отрезок обязан строго сокращаться на каждой итерации.

## `(left + right) / 2` и переполнение

В Java и C++ сумма двух больших `int` переполняется, и середина уезжает в отрицательные числа — знаменитый баг, живший в стандартной библиотеке двадцать лет. Правильная форма — `left + (right - left) / 2`.

В JavaScript числа — 64-битные double, целые точны до 2⁵³, так что переполнения нет. Но привычка полезная, а читается не хуже.

Осторожнее с `>> 1` вместо `/ 2`: битовые операции в JS работают с 32-битными целыми, так что на индексах больше 2³¹ сдвиг сломается. Для массивов такого размера это неактуально, для бинпоиска по ответу — вполне.
